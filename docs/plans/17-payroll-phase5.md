# 17 - Payroll phase 5: publish maker-checker, bank payment file, investment declarations / Form 16, TDS engine

Status: PROPOSED. Branch `feature/payroll-phase2` (or `feature/payroll-phase5` cut from it). Source: plan 14 phase 5 (items 19, 21, 22, 4).
Contract: `docs/api-contract.md` section 19 (single source of truth; this plan only explains it). Migrations `0027` (5a), `0028` (5b), `0029` (5c).
All plan 12 / 15 / 16 rules still apply: money as 2-decimal strings / `Decimal`, every amount and identifier encrypted at rest, no SQL aggregates on money (D2), audit every view/change
without amounts or identifiers, step-up (`current_password`) on sensitive writes, nobody acts on their own money (D9), published = locked (D4), maker-checker with the
creator / last editor / submitter / append-only `contributors` exclusion (18.14), lock order of plan 16 F15. Nothing is deployed until the user approves.

## 0. What exists today (read from the code, `services/payroll_runs.py::_check_second_person`)
- `payroll.publish_requires_second_person` (default false; change needs `role.assign` + step-up). When the run snapshot OR the current value is on, run / payslip publish refuse
  (403 `SECOND_PERSON_REQUIRED`) a caller who is `run.processed_by` or the `processed_by` / `updated_by` of a payslip being published. That is all.
- Gaps (same bug classes as the 4a / 4b reviews):
  - **G1 last-editor only.** A edits a payslip, B processes the run (B becomes `updated_by`): A can publish what A typed. No contributor history.
  - **G2 component makers ignored.** A creates a 1,00,000 bonus (17.2), accepts arrears, reschedules a loan, approves a claim or an overtime day, or creates a first structure; B processes; A publishes.
  - **G3 not bound to what was reviewed.** No request / queue; the publisher publishes whatever is processed at that moment (reopen + edit + process by a third person in between is not noticed by the checker).
  - **G4 no UI.** Flutter only shows the 403 message; nobody is told a publish is waiting.
- Bank: only the `bank_advice` xlsx (15.1, from the payslip `identity` snapshot). No payment tracking, so the same salary can be sent twice and a bank-account change just before payday is not flagged.
- TDS: manual only (`salary_structures.tds_monthly`, payslip `inputs.tds`). No declarations, proofs, Form 16, or 24Q data.

## 1. Design decisions
| # | Decision |
|---|---|
| G1 | **Publish requests.** While maker-checker is on (run snapshot OR current setting, as today), direct `POST /runs/{id}/publish` and `POST /payslips/{id}/publish` answer 409 `PUBLISH_REQUEST_REQUIRED`. A maker (`payroll.manage`) creates a publish request for a processed run (scope `run`) or one processed payslip of a published run (scope `payslip`: held / revision). The checker (`payroll.publish` + step-up) approves, and the publish runs in the same transaction. Reject = request closed, run unchanged. Setting off: today's behaviour, request endpoints 409 `MAKER_CHECKER_OFF`. |
| G2 | **Bound snapshot.** The request stores the exact set `{payslip_id, version, result_mac}` of processed non-held payslips, `run.processed_at`, counts and totals (encrypted). `result_mac = HMAC-SHA256(HKDF(secret, "payroll-publish-snapshot"), canonical JSON of result + inputs + identity)`: an HMAC, never a plain hash (amounts are low-entropy and a plain hash could be brute-forced). Approve publishes exactly that set; any difference (set, version, mac, processed_at) -> 409 `PUBLISH_STALE`. Reopen, refresh, a payslip-level process / reopen and expiry (`payroll.publish_request_ttl_hours`, 72) mark open requests `stale` in the same transaction. One open request per run / payslip (partial unique). |
| G3 | **Maker set (who cannot approve).** Computed fresh under locks at approve and stored on the request row: requester; run `contributors` (create, refresh, process, reopen); payslip `contributors` of every payslip in the set (new append-only column: every PUT / process / reopen / revise / refresh that changes the row adds the actor; backfilled from `created_by`, `updated_by`, `processed_by`); actors of non-lifecycle events in `payroll_item_events` for every component source pulled into those payslips (create / update / accept / approve / reschedule / skip / review; NOT `process`, `reopen`, `pay`, `carry`); for rows with `fnf_id`, the F&F's creator / last editor / submitter / contributors instead (its checker is not a maker); `created_by` / `updated_by` of `manual` / `import` structures used by the set (`increment` structures were already maker-checked). The employee of a scope-`payslip` request is 403 `FORBIDDEN`; a run that contains the checker's own payslip keeps the existing `self_included` rule. DB: `CHECK (decided_by IS NULL OR (decided_by <> requested_by AND decided_by::text <> ALL (makers)))`. |
| G4 | **Publish-check endpoint** tells the UI who may request / approve and why not (reason codes per maker: `PROCESSED_RUN`, `EDITED_PAYSLIP`, `CREATED_COMPONENT`, `CREATED_STRUCTURE`, `REQUESTED`, `FNF_MAKER`), so the screen never offers a button that will 403. |
| B1 | **Payment batches are always maker-checker** (the switch `payroll.bank_file_requires_second_person` was removed in the 5a security review: the second approver is unconditional). `draft -> submitted -> approved -> exported -> closed` (+ `rejected` back to draft, `cancelled`). Maker `payroll.manage`; checker `payroll.approve` + step-up, not the creator / last editor / submitter / contributors, not the employee of any line (that line fails, see B4), and not the person who changed the bank details of any line employee in the last `payroll.bank_change_alert_days` (30). |
| B2 | **Lines come from published live payslips only** (`payment_mode = bank_transfer`, not held, net > 0). Beneficiary data = the payslip `identity` snapshot (what the publish checker reviewed). If the current payroll details differ, the line is flagged `BANK_DETAILS_CHANGED` and the maker must choose `account_source: snapshot | current` per flagged line (default `snapshot`); the checker sees both masked (last 4 + IFSC). |
| B3 | **No double payment.** One live line per payslip (partial unique on `payslip_id` where status in `pending, exported, paid`). A revision pays only the delta: `amount = live net - sum(paid lines of the supersedes chain)`; delta < 0 -> not in the file, blocker `RECOVERY` (handled by HR outside or as a deduction next month). `failed` lines free the slot for a new batch. |
| B4 | **Approval bound to the submitted lines.** Submit freezes the lines (trigger) and stores `lines_mac` (HMAC over line id, payslip id, version, amount, account fields). Approve re-derives every line from the live payslip and current details: payslip superseded, held, amount or account changed, or details changed since submit -> 409 `BATCH_STALE` (nothing approved; maker withdraws and resubmits). Lines whose employee is the checker -> 403 `FORBIDDEN` for the whole batch (the checker cannot approve a batch paying themselves; another approver must). |
| B5 | **File = stored lines, never a recomputation.** `POST /file` (step-up) renders the CSV from the approved, encrypted lines; first download sets `exported`, stores `file_sha256`; later downloads are byte-identical and audited. Format: generic NEFT bulk CSV (section 19.5), ASCII only, names reduced to bank-safe `[A-Z0-9 .]`, fixed narration, so no CSV formula injection is possible (a name that becomes empty is a `NAME` blocker). |
| B6 | **Confirmation.** `confirm` marks lines `paid` / `failed` with an optional bank reference (encrypted); batch `closed` when no line is `exported`. Company debit accounts live in `company_bank_accounts` (encrypted, immutable number / IFSC; create a new one to change; `admin_alert` on create). |
| D1 | **Payslip delivery stays push-only** (no email / WhatsApp without a provider). New `payslip_deliveries` row per published payslip (pushed_at, push_count, first_viewed_at, first_downloaded_at, written by the existing employee view / PDF endpoints). HR sees a delivery report and can send a reminder push (max 1 per payslip per 24 h, 3 in total). |
| T1 | **Tax year rules are data, verified by a second person.** `tax_year_rules` (per FY, versioned): regimes, slabs, standard deduction, rebate, surcharge, cess, rounding, section catalogue and limits, HRA rule, component treatment, no-PAN rate, form / section labels. `draft -> submitted -> verified` (+ `superseded`); verifier = `payroll.approve` + step-up + attestation text, not a contributor. Verified rows are immutable (trigger); a correction is a new version. The Python code holds NO slab, rate or limit constant; the migration seeds FY 2026-27 as a `draft` marked `UNVERIFIED` (values copied from FY 2025-26 as known when written) that nothing uses until verified. |
| T2 | **Declarations need verified rules.** Employee declaration endpoints answer 409 `TAX_RULES_NOT_VERIFIED` until the FY has a verified version (employees never see unverified limits). |
| T3 | **Drafts never feed tax.** `tax_declarations` keeps `draft_enc` (what the employee is editing) and `submitted_enc` + `submitted_version` (frozen at submit). Only `submitted_enc` and `verified` proofs feed the engine; editing after submit changes nothing until resubmitted. Same pattern as the 4b LWD fix. |
| T4 | **Proofs are maker-checker.** Employee uploads (files purpose `tax_proof`); HR (`payroll.manage`) verifies with `expected_version` and a verified amount (<= claimed, <= MAX); verifier is not the employee and not the person who entered the declaration on the employee's behalf (DB CHECK). |
| T5 | **Form 16 is uploaded, not generated.** Part A must come from TRACES and the signed certificate from the employer / tax consultant, so HR uploads PDFs (`form16`, `part_a`, `part_b`, `form12ba`), matched to employees by PAN or Employee ID in the file name; dry run bound to commit by HMAC (17.2 pattern); publishing to employees needs a second person (`payroll.approve` + step-up, not the uploader; setting `payroll.form16_requires_second_person`, default true). The original file name (contains the PAN) is never stored, logged or audited. |
| T6 | **TDS engine off by default.** `payroll.tds_engine_enabled` (false; change = `role.assign` + step-up + `admin_alert`) and `payroll.tds_engine_mode` `suggest` (default: computed TDS shown beside the manual figure; payslip unchanged) or `apply` (engine sets the TDS line; HR override needs a reason, warning `TDS_OVERRIDDEN`). Off = exactly today's manual TDS. A run snapshots the mode and the verified rules version; `refresh` adopts newer ones. |
| T7 | **Engine method (s.192 average rate, per verified rules).** Annual income = taxable earnings of this employer's published payslips in the FY + this month + projection of the structure in force for the remaining employed months (to March, or to the LWD) + previous employer income (declared, proof-verified after the proof month) + other income (only when `payroll.tds_include_other_income`). Less exemptions (HRA least-of-three, old regime only), standard deduction, PT (when the regime allows), Chapter VI-A within section and group limits (declared before `payroll.tds_proofs_from_month`, verified proofs from that month). Tax by slabs, rebate with marginal relief, surcharge with marginal relief, cess, rounding per rules. Remaining = annual tax - TDS already deducted this FY - previous employer TDS; monthly = rupee-round(remaining / remaining months incl. this one), >= 0. One-time earnings: the extra tax they cause is taken in the month paid (`payroll.tds_one_time_in_month`, true). No PAN: higher of the average rate and `no_pan_min_rate_pct`. Capped so net pay >= 0 (`TDS_CAPPED_NET`). |
| T8 | **Computation snapshot.** Each draft / processed payslip has one `payroll_tax_computations` row (rules id + version, regime, declaration version, proofs digest, encrypted computation, suggested TDS); frozen by trigger once the payslip is processed; included in the publish `result_mac`, so a changed declaration after the publish request makes it `PUBLISH_STALE` only if the run is refreshed. |
| T9 | **Statutory outputs are working data.** 24Q quarterly xlsx (deductees, Q4 salary annexure, challans, blockers) for the user's return utility, and a per-employee "Tax computation statement" PDF (watermark "Not Form 16"). TDS challans gain BSR code / challan serial / deposit date. Nothing is filed by the app. |
| L | **Lock order (extends plan 16 F15).** Global: `payroll_runs -> users -> payslips -> salary_structures -> tax_year_rules (share) -> tax_declarations (share) -> tax_proofs (share) -> payroll_one_time_items -> ... -> fnf_settlements -> payroll_tax_computations -> payroll_publish_requests` (request row LAST, version re-checked). Payments: `payroll_runs (share) -> payroll_payment_batches -> payroll_payment_lines -> payslips (share) -> employee_payroll_details (share)`; publish never locks payment rows, so no cycle. Tax admin: `tax_year_rules -> tax_declarations -> tax_proofs`. |

### Lessons from the 4a / 4b security fixes, applied
- Drafts must not alter eligibility or outputs: draft declarations, unverified rules, draft / submitted payment batches, unpublished Form 16 and open publish requests change nothing (T1-T3, B4, G1).
- Approvals bound to what was reviewed: publish `result_mac` set (G2), batch `lines_mac` + re-derivation (B4), rules verify bound to `expected_version` + `rules_sha256` (T1), proof verify `expected_version` (T4), Form 16 publish bound to listed `{id, sha256}` (T5).
- Maker exclusion by full history: `contributors` arrays only grow (trigger), DB CHECKs on every decision column, event-history makers for components (G3).
- Tagged-row integrity: payment lines must reference a payslip of the batch's run and the same `user_id` (trigger); tax computations must match their payslip's user and FY; proofs must match their declaration's user and FY (triggers, 23000 -> 409 `CONFLICT`).
- Money caps: every amount <= 10,000,000.00 (annual tax figures <= 120,000,000.00); line amount <= payslip net; batch total computed server-side, never accepted from the client; verified proof <= claimed.
- Redaction: audit / push / log carry ids, periods, FY, counts and codes only; never amounts, PAN, accounts, IFSC, landlord / lender PAN, file names, references or comments. Allow-list keys in 19.11.
- Step-up on every approve: 5/min and 20/day per admin (fail closed), as 18.4.

## 3. Business rules and edge cases
**Publish requests (5a)**
- Create: run `processed` (scope run) or payslip `processed` in a `published` run (scope payslip); something to publish (409 `NOTHING_TO_PUBLISH`); no open request (409 `PUBLISH_REQUEST_EXISTS`); payslips with errors cannot be processed already.
- The requester may hold `payroll.publish` too; they still cannot approve their own request. Withdraw: any `payroll.manage` holder (becomes a contributor of the run).
- Approve check order: step-up, scope employee (403 `FORBIDDEN`), maker set (403 `SECOND_PERSON_REQUIRED`), `submitted` (409 `NOT_SUBMITTED`), `expected_version`, expiry (409 `PUBLISH_STALE` reason `EXPIRED`), run still processed, snapshot equality (`PUBLISH_STALE`), then the existing publish (409 `COMPONENTS_CHANGED`, `FNF_NOT_INCLUDED` roll back everything and leave the request `submitted`).
- Turning the setting off while a request is open: the run snapshot still says on, so the request path stays mandatory for that run (existing M1 rule).
**Payments (5a)**
- Batch create: run `published`; scope `user_ids` or all eligible; at most 1000 lines; blockers listed, not lines: `NO_BANK_DETAILS`, `INVALID_ACCOUNT`, `INVALID_IFSC`, `NAME`, `NOT_BANK_TRANSFER`, `HELD`, `ZERO_NET`, `ALREADY_PAID`, `IN_OTHER_BATCH`, `RECOVERY`.
  Warnings: `BANK_DETAILS_CHANGED`, `RECENT_BANK_CHANGE` (changed within `bank_change_alert_days`), `REVISION_DELTA`, `NO_PAN`.
- `value_date` today..today + 30 (office timezone); debit account active. Edit only in draft (exclude / include lines, account source, value date, debit account).
- Export marks lines `exported`; confirm `paid` / `failed`; a `failed` line can go into a new batch. Cancel only before export. A superseded payslip with an exported / paid line is fine (the revision pays the delta).
**Delivery (5a)**: `payslip_deliveries` row is created at publish; `first_viewed_at` / `first_downloaded_at` are set by `GET /payslips/{id}` / `/pdf` for the owner. Reminder: only published, not viewed, device registered.
**Rules (5b)**: validation: slabs contiguous from 0.00, last open-ended, rates 0..50 (2 decimals), money <= caps, section codes `^[A-Z0-9_]{2,16}$`, <= 40 sections, group limits reference existing groups, windows inside the FY (proof window may run to 31 March). New version = copy of the latest; submit freezes; verify by a non-party with the attestation; the previous verified version becomes `superseded` in the same transaction.
**Declarations (5b)**
- Edit / submit only inside the declaration window, or the proof window for proof items, or until `unlocked_until` (HR unlock, reason). Regime may change until the declaration window closes; after that it is fixed for the year (Q-L2); no declaration = the rules' `default_regime` (new), flag `REGIME_DEFAULT`.
- Items: <= 40; amount 0.01..MAX (rent monthly <= 10,000,000.00; annual amounts <= 120,000,000.00); per-section fields from the rules (landlord PAN required when annual rent > `landlord_pan_above`; PAN format 13.4); sections not allowed by the chosen regime are accepted but flagged `NOT_IN_REGIME` and ignored by the engine.
- HR entry on behalf (`payroll.manage` + step-up, not self) sets `entered_by`; the employee gets `tax_declaration_changed`.
- Proofs: one or more per item, 1..5 files each (own unused `tax_proof` uploads), claimed <= item amount; verify `verified_amount` <= claimed; reject needs a comment; employee may cancel while `submitted`.
**Form 16 (5b)**: up to 20 PDFs per upload request (<= 2 MB each, PDF magic + existing PDF checks); name must contain exactly one employee PAN or one Employee ID token, else `UNMATCHED` / `AMBIGUOUS`; an existing live document of the same kind -> `REPLACES` warning (commit withdraws the old one). Publish lists `{id, sha256}` reviewed; employee sees only `published`.
**TDS engine (5c)**
- Runs at run create / refresh / process / revise and payslip process, never at publish; in `apply` mode `inputs.tds` becomes the engine value unless HR set an override (reason 3-200, `TDS_OVERRIDDEN`).
- Remaining months: from this month to March, ending at the LWD month for an approved F&F (all remaining tax in the final payslip), joiners from their join month (previous employer data via `PREV_EMPLOYER`).
- Over-deduction: monthly 0, flag `TDS_EXCESS` (no refund through payroll). TDS above net -> capped, `TDS_CAPPED_NET`, shortfall carried to the next months.
- Flags: `NO_PAN_206AA`, `NO_DECLARATION`, `REGIME_DEFAULT`, `RULES_CHANGED` (a newer verified version exists than the run snapshot), `PERQUISITE_REVIEW` (outstanding employee loans > the rules' `loan_perquisite_threshold`, perquisites are not computed, Q-L8), `LEAVE_ENCASH_REVIEW`.
- Engine enabled but no verified rules for the FY: payslip warning `TAX_RULES_NOT_VERIFIED`, manual TDS used (never a silent zero).
- 24Q: published payslips of the quarter; blockers `NO_PAN`, `CHALLAN_MISSING` (month has TDS > 0 and no paid challan with BSR / serial).

## 5. Security considerations
- Maker-checker three times (service, DB CHECK, audit `maker_id`/`checker_id`) for publish requests, payment batches, rules verification, proofs, Form 16 publish. `contributors` and `makers` only grow.
- Step-up: publish approve, batch approve, bank file download, confirm, bank account create, Form 16 commit / publish / withdraw, rules verify, declaration on behalf, 24Q and statement exports, every protected setting. 5/min + 20/day on approvals.
- Bank fraud controls: snapshot accounts, `BANK_DETAILS_CHANGED` choice visible to the checker, recent-change checker exclusion, one live line per payslip, immutable debit accounts, `admin_alert` push to `role.assign` holders after each bank file download and debit account creation.
- Files: proofs and Form 16 encrypted at rest; access = owner, `payroll.view_all` (proofs, Form 16 any status), cross-user reads audited `file.view_other`; employee Form 16 only `published`; 404 + `payroll.denied` for probes. Original file names discarded (PAN). PDFs served `no-store`, `nosniff`, CSP as 13.8.
- CSV: ASCII, bank-safe characters only, fixed columns, no user free text except cleaned names; `Content-Disposition` fixed name `bank-PAY-2026-10-01.csv`.
- Tax data: declarations hold third-party identifiers (landlord / lender PAN): encrypted, masked in admin lists, revealed only in the detail with audit, never in xlsx unless `include_identifiers` + step-up.
- Rules are not secret but drive money: integrity by verification + immutability + run snapshot of `rules_id`/`version`; the engine refuses unverified rules.
- Redaction allow-list (19.11). Push payloads: names, periods, FY, counts only.
- nginx: exact location `/api/admin/payroll/tax/form16/upload` with a 42m body; everything else unchanged.

## 8. Open questions for the user (defaults are built if unanswered; LEGAL items need the user / auditor / tax consultant)
- **Q-L1 LEGAL - which law and forms apply to FY 2026-27.** To our knowledge the Income-tax Act, 2025 replaces the 1961 Act from 1 April 2026, renumbering sections (s.192 TDS on salary) and possibly renaming Form 16 / 24Q; FY 2026-27 rates come from the Finance Act 2026, which we have not verified.
  Default: the seeded FY 2026-27 rules are a `draft` copy of FY 2025-26 (new regime: nil to 4 L, 5/10/15/20/25/30% in 4 L steps above that, standard deduction 75,000, 87A rebate up to 12 L taxable income (max 60,000); old regime: 2.5 L / 5 L / 10 L at 5/20/30%, standard deduction 50,000, rebate up to 5 L (max 12,500); cess 4%; surcharge 10/15/25/37%, capped at 25% in the new regime).
  Section / form names are labels in the rules data. Nothing uses the seed until a second person verifies it.
- **Q-L2 LEGAL - regime.** Default: new regime unless the employee declares old; the employee may change it until the declaration window closes, then it is fixed for the year's TDS (they can still choose differently in the return).
- **Q-L3 LEGAL - projection method.** Default: average-rate method with one-time earnings taxed in the month paid; declared investments used until 31 December, only verified proofs from January (`tds_proofs_from_month` = 1); other income only when the setting is on. Confirm.
- **Q-L4 LEGAL - HRA and deductions.** Default: HRA least-of-three (actual HRA, rent - 10% of basic, 50% metro / 40% non-metro of basic; metros Delhi, Mumbai, Kolkata, Chennai), landlord PAN needed above 1,00,000 rent a year; 80C group 1,50,000; 80CCD(1B) 50,000; 80D 25,000 / 50,000 (senior); 24(b) 2,00,000; LTA not computed. Confirm the list and limits each year.
- **Q-L5 LEGAL - no PAN.** Default: TDS at the higher of the average rate and 20% (s.206AA rule as known). Confirm under the new Act.
- **Q-L6 LEGAL - component treatment.** Default: reimbursements exempt (genuine business expenses with bills), leave encashment while in service taxable, leave encashment at exit taxable with `LEAVE_ENCASH_REVIEW` (exemption not computed), gratuity outside payroll, overtime / bonus / arrears taxable. Confirm (especially phone / internet reimbursements).
- **Q-L7 LEGAL - Form 16.** Default: Part A from TRACES and the signed Form 16 are uploaded by HR; the app does not generate a signed Form 16. Our computation statement is working data only. Confirm who signs and whether Part B should be generated by the app later.
- **Q-L8 LEGAL - perquisites.** Interest-free / concessional employee loans above the threshold (rules data, default 20,000 aggregate as known) are a taxable perquisite; other perquisites and employer NPS (80CCD(2)) are not computed. Default: `PERQUISITE_REVIEW` warning only. Confirm.
- **Q-L9 LEGAL - 24Q / return.** Default: the app produces working xlsx for the return preparation utility; the user (or consultant) prepares and files the return and Form 27A. Confirm the utility and the column layout.
- **Q-L10 LEGAL - data retention.** Declarations and proofs contain third-party personal data (DPDP Act, 2023). Default: kept 8 years after the FY, no automatic purge in this phase; the declaration screen shows a short notice. Confirm the retention period.
- **Q-L11 LEGAL - bank file.** Default: generic NEFT CSV (layout 19.5), payment type `NEFT` for every line. Banks have their own bulk formats and RTGS limits; confirm the bank and, if needed, its exact template (a new format value can be added).
- **Q1** Publish: while maker-checker is on, direct publish is refused and every publish goes through a request; component and structure makers count as makers (strict; a two-person HR team may need an admin to approve). Confirm.
- **Q2** Payment batches need a second person by default (`payroll.approve`), and a person who changed an employee's bank account in the last 30 days cannot approve a batch paying that employee. Confirm.
- **Q3** Form 16 publishing needs a second person; employees see only published documents. Confirm.
- **Q4** TDS engine: off by default; when enabled, `suggest` mode first; `apply` only after the user has compared at least one month's suggestions with the manual figures. Confirm.
- **Q5** Delivery: push only, reminders max 3 per payslip, no email / WhatsApp until a provider is supplied.
- **Q6** HR may enter a declaration on an employee's behalf (step-up, employee notified, entrant cannot verify the proofs). Confirm.
